Fidelis — design

The idea

Three layers. Change is detected once, in the middle layer, and everything built on it follows.

Layer Holds Example
Docs Pages split into sections Container Registry · Overview
Graph Concepts (name, exam section) and facts (statement + verbatim quote + page + status) "GKE clusters can pull images directly from Container Registry"
Content Questions, each listing the fact ids it was built from q1 → f3, f4

Pipeline

  1. Choose the source of truth (code): the docs pages everything is built from. The demo starts with Cloud Storage only.
  2. Build graph (LLM, one call per page): concepts mapped to exam sections, and 2–5 facts per page, each with a quote copied from the page. Code verifies every quote really appears in the page.
  3. Generate questions (LLM, one call): the most important questions from the graph. Each records its fact ids.
  4. Docs updated (code): the new versions arrive; the UI shows a word diff per page.
  5. Update graph (LLM, one call per page). For every fact: given the updated docs, is this still true? → still_true, changed (with a corrected fact and new quote) or removed. The same call returns facts the update added: things the new version states and the old version did not. It gets both versions of the page, and code drops any "new" fact whose quote was already in the old version. All updated docs are included as context, because a deprecation is often announced on another page.
  6. Update content and review (LLM). Only questions built on a changed or removed fact go back, with the old and new facts and quotes and the updated docs. The LLM judges the whole question and returns keep or rewrite; if what it tests no longer exists, the rewrite tests its replacement. New or corrected facts that no question covers go to one more call that proposes new questions, given the existing ones so it does not duplicate them. A person can then approve, reject or undo each change.

One question, start to finish

Step What happens
Build graph From the Container Registry page: "GKE clusters can pull images directly from Container Registry", with its quote
Generate q1: deploy a Cloud Build image to GKE with the fewest steps. Answer: push to Container Registry, GKE pulls it
Update graph That fact → changed; corrected fact "…from Artifact Registry" with the new quote; new fact "Container Registry is deprecated"
Update content q1 cites a changed fact → rewrite: Artifact Registry in the answer and explanation, citing the corrected facts; wrong options unchanged
Review q1 hidden until approved; the reviewer sees old and new facts, quotes and question side by side

Where people come in

  • Review switch (on by default). On: every change waits for a person, and questions built on a changed fact are hidden from learners meanwhile; rejecting shows them again. Off: changes that pass the code checks apply automatically.
  • Code checks run either way: a stem and an explanation, exactly 4 distinct options, an answer index that points at one, at least one linked fact, and every linked fact current with its quote found in the updated docs. A change that fails a check always waits for a person.
  • Evidence, not just output. The reviewer sees the old fact and quote beside the new ones, and the old question beside the new one with word-level highlights.
  • Undo. Every applied change keeps the previous version and can be reverted.

Decisions

Decision Chosen Instead of Why
Core check One question per fact: still true? Categories of change (rename, deprecation, restructure…) with rules for each One check covers every kind of change
Graph Concepts + facts with verbatim quotes Graph database; concept lifecycle (deprecated, successor, exam status) Every claim traces to a sentence; changed facts already say what a status would
Content from the graph Questions link to fact ids Questions generated straight from docs The link is what makes healing targeted
Context for checks Each page's facts checked against all updated pages Only the same page A deprecation is often announced on another page
Re-check scope Only questions on changed facts Every question Unaffected content costs nothing
Content changes Rewrite or new Also retire A question on something that no longer exists is rewritten to test its replacement
Approval Code checks + optional human LLM approving its own output A model grading itself is not a safeguard
LLM access One callLlm(prompt, zod schema) over any OpenAI-compatible API (Vercel AI SDK; Gemini free tier by default) Several modes (replay, CLI) One path to understand and test; malformed output fails visibly
Tests A scripted mock model Recorded responses No key, no recording that breaks when a prompt changes
Orchestration Plain async functions, one per step Mastra / LangGraph A fixed sequence of steps needs no agent framework
Storage One JSON file Supabase Zero setup for reviewers; one module to swap

Limits and next steps

  • Only extracted facts are checked. The new-question step reads new docs directly, which partly covers what extraction missed.
  • Each check sends all updated docs, which only works because they are short. At scale: retrieve relevant pages first, and only re-check facts from pages whose text changed.
  • Exam-guide changes (topics added or dropped) are not tracked; the guide is used only to map concepts to sections.
  • LLM judgments are shown, not measured. Next: a labelled set of fact changes with expected verdicts, scored on every prompt change.
  • Steps run inside one web request; production would use a job queue with retries, and Postgres for state.
  • Lessons or study guides would hang off the same facts and update the same way.
